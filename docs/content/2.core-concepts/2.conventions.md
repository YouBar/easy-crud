title: The conventions table
description: Patterns, placeholders and candidates — how a role name becomes a class name.
---

easy-crud ships **no conventions at all**. It makes no assumption about where
your classes live, or that you have them. Until you add a row, nothing is looked
up — responses use a plain `JsonResource` and nothing is validated.

```php [config/easy-crud.php]
'conventions' => [
    //
],
```

Add the rows you want. These are what most Laravel applications end up with:

```php [config/easy-crud.php]
'conventions' => [
    'resource' => ['App\Http\Resources\{Model}Resource'],
    'request'  => [
        'App\Http\Requests\{Action}{Model}Request',    // make:model -a
        'App\Http\Requests\{Model}\{Action}Request',   // nested by model
    ],
],
```

Nothing above is special-cased. `request` is resolved per action, the others per
model, and any row you add is resolved the same way.

## What a row does, and does not, do

A row answers one question — *which class is this role, for this model* — and
then stops. It does not decide what happens to that class.

Deciding what to do with a resolved class is hardcoded, and the package only
does it for three roles:

| Role | What the package does with it |
|---|---|
| `resource` | Wraps a model or paginator for the response |
| `collection` | Wraps an index result, if a collection class exists |
| `request` | Validates the action, resolved per action |

Any other row resolves a class and nothing reads it. That is not a limitation —
it is how you attach your own layer without the package guessing at it. Add the
row, then consume it in an override: see
[custom roles](/customisation/custom-roles) for the mechanics, and
[applying your own patterns](/customisation/design-patterns) for a worked
service and repository example.

## Value shapes

| Value | Meaning |
|---|---|
| `null` | Role disabled. Never looked up. |
| `'App\Foo\{Model}Bar'` | One pattern. |
| `['A\{Model}', 'B\{Model}']` | Ordered candidates — the first class that exists wins. |
| `fn ($model, $action) => ?string` | Compute it yourself. |

## Placeholders

For `App\Models\Course` and the `store` action:

| Placeholder | Value | Placeholder | Value |
|---|---|---|---|
| `{Model}` | `Course` | `{model}` | `course` |
| `{Models}` | `Courses` | `{models}` | `courses` |
| `{Action}` | `Store` | `{action}` | `store` |
| `{Namespace}` | `App\Models` | `{Domain}` | `App` |
| `{FQCN}` | `App\Models\Course` | `{SubNamespace}` | `` (see below) |

## `{SubNamespace}` — for models grouped into folders

Models often sit in subfolders: `App\Models\Billing\Payment` alongside
`App\Models\Post`. `{SubNamespace}` is where a model sits below your model
root, so a single pattern covers both.

Tell it where models start:

```php [config/easy-crud.php]
'model_namespace' => 'App\Models',

'conventions' => [
    'resource' => ['App\Http\Resources\{SubNamespace}\{Model}Resource'],
    'request'  => ['App\Http\Requests\{SubNamespace}\{Model}\{Action}Request'],
],
```

| Model | `{SubNamespace}` | Resolves to |
|---|---|---|
| `App\Models\Post` | `` | `App\Http\Resources\PostResource` |
| `App\Models\Billing\Payment` | `Billing` | `App\Http\Resources\Billing\PaymentResource` |

The empty segment collapses, so top-level models need no separate pattern.

::note
`model_namespace` is only read by `{SubNamespace}`. A pattern using the
placeholder without it set is a configuration error rather than a silent miss.
::

## `{Domain}` — for modular and DDD layouts

`{Domain}` is the model's namespace **minus its final segment**. It exists so that a layout like this needs no closure:

```
Domain/Courses/Models/Course.php
Domain/Courses/Resources/CourseResource.php
Domain/Courses/Requests/StoreRequest.php
```

```php
'conventions' => [
    'resource' => '{Domain}\Resources\{Model}Resource',
    'request'  => '{Domain}\Requests\{Action}Request',
],
```

`{Domain}` resolves to `Domain\Courses`, and both patterns land.

## Closures

When no pattern fits, compute the class yourself:

```php
'resource' => function (string $model, ?string $action): ?string {
    return match ($model) {
        Legacy\Order::class => Legacy\OrderPresenter::class,
        default => 'App\Http\Resources\'.class_basename($model).'Resource',
    };
},
```

Return `null` to mean "nothing", which triggers the [fallback](/core-concepts/fallbacks).

## Per-action resolution

`request` is resolved per action, so `index` and `show` can have request classes too. That is how you validate filter and sort query parameters without touching the controller:

```
App\Http\Requests\IndexPostRequest   → validates ?filter[…] and ?sort
App\Http\Requests\StorePostRequest
```

## Performance

Resolution is memoised per request, keyed by role + model + action, and **misses are cached as misses** — a miss is an autoloader round trip, so it is the expensive case. Nothing re-resolves inside a single request.
