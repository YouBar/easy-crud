---
title: Applying your own patterns
description: Putting easy-crud in front of a service, action or repository layer.
---

easy-crud has no opinion about where your business logic lives. It writes to
Eloquent by default, and every write is a method you can point somewhere else.

```php
protected function create(array $data): Model;
protected function applyUpdate(Model $model, array $data): Model;
protected function delete(Model $model, array $data = []): void;
```

## The direct way

Override the method and call whatever you like:

```php
class PostController extends CrudController
{
    protected string $model = Post::class;

    protected function create(array $data): Model
    {
        return app(CreatePost::class)->handle($data);
    }

    protected function applyUpdate(Model $model, array $data): Model
    {
        return app(UpdatePost::class)->handle($model, $data);
    }
}
```

That is the whole integration. Nothing needs configuring, and it works the same
for an action class, an invokable, a command bus or a plain static call.

## The same pattern across many controllers

Repeating the class name in thirty controllers is the part worth removing, not
the override itself. Add a row to the conventions table so each model finds its
own collaborator, then write the override once in your own base class.

::steps{level="3"}
### Name the pattern

```php [config/easy-crud.php]
'conventions' => [
    'service' => ['App\Services\{Model}Service'],
],
```

`service` here is your name, not the package's. easy-crud resolves the class and
does nothing else with it — see [custom roles](/customisation/custom-roles).

### Consume it once

```php
abstract class ServiceController extends CrudController
{
    protected function create(array $data): Model
    {
        return $this->resolved('service')->create($data);
    }

    protected function applyUpdate(Model $model, array $data): Model
    {
        return $this->resolved('service')->update($model, $data);
    }

    protected function delete(Model $model, array $data = []): void
    {
        $this->resolved('service')->delete($model, $data);
    }
}
```

### Extend it

```php
class PostController extends ServiceController
{
    protected string $model = Post::class;
}
```
::

`App\Services\PostService` is now found and used, and so is every other
`{Model}Service` you write.

## Handling a partial layer

Not every model has a service. `resolved()` returns `null` when nothing matched,
so fall back rather than requiring one everywhere:

```php
protected function create(array $data): Model
{
    return $this->resolved('service')?->create($data)
        ?? parent::create($data);
}
```

## Reading as well as writing

The same applies to the index query. `scope()` narrows what the actor may see,
`filter()` applies what they asked for:

```php
protected function scope(Builder $query): Builder
{
    return $this->resolved('service')?->scope($query) ?? $query;
}

protected function filter(Builder $query): mixed
{
    return $this->resolved('service')?->filter($query) ?? $query;
}
```

::note
`filter()` may return any object that forwards to a builder, which is why its
return type is loose. A wrapper like `spatie/laravel-query-builder` does not
extend Eloquent's `Builder`.
::

## Repositories, in full

The same shape with a different name and different methods:

```php [config/easy-crud.php]
'conventions' => [
    'repository' => ['App\Repositories\{Model}Repository'],
],
```

```php
abstract class RepositoryController extends CrudController
{
    protected function create(array $data): Model
    {
        return $this->resolved('repository')->store($data);
    }
}
```

Nothing in the package knows what a repository is, which is exactly why it fits.
