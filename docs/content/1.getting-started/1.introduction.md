Most Laravel APIs contain the same controller forty times. It lists a model with pagination, shows one, creates one, updates one, deletes one. The interesting part is usually three lines in the middle; the rest is scaffolding you have typed before.

`easy-crud` writes that scaffolding once.

```php
class PostController extends CrudController
{
    protected string $model = Post::class;
}
```

```php
Route::crud('posts', PostController::class);
```

That is a working, paginated, policy-aware JSON API.

It is also completely unopinionated about the rest of your application. easy-crud ships no conventions, so out of the box it returns plain JSON and validates nothing. Tell it where your resource and request classes live — [one config entry each](/core-concepts/conventions) — and it finds them for every model from then on, with no change to any controller.

## What it assumes about your project

Nothing. Every class easy-crud looks for is described by a pattern in a config file you own, and the table ships empty. A plain Laravel app, a modular monolith and a DDD layout are all just different patterns — there is no built-in default to work around.

## How it works

Every action runs the same pipeline:

```
resolve → authorize → validate → act → prepare → transform → respond
```

Each step has a default, and each default is a `protected` method on the
controller. `find()` resolves the model from the route, `authorizeAction()`
checks a policy if one exists, `validated()` validates if there is anything to
validate with, `create()` / `applyUpdate()` / `delete()` touch the database,
`transform()` wraps the result in a resource. Override one and the rest carry
on unchanged — see [overriding a method](/customisation/overriding-methods) for
the full list, or [the five actions](/actions/overview) for which steps each one
runs.

Two things decide what those defaults do:

- **[The conventions table](/core-concepts/conventions)** answers *which class*
  is the resource or request for a given model. It is data: patterns
  like `App\Http\Resources\{Model}Resource`, in a config file you own.
- **[The precedence ladder](/core-concepts/precedence)** decides *which answer
  wins* when there is more than one: a property on the controller, then a method
  override, then the config pattern, then a fallback. The same four rungs for
  every role.

A row only ever answers *which class*. What happens to that class is built in
for resources, collections and requests, and is yours to write for anything
else — which is how you put
[your own service, action or repository layer](/customisation/design-patterns)
behind it.

## What it is not

- **Not a query builder.** Filtering and sorting are yours — [wire up spatie/laravel-query-builder](/recipes/query-builder) in three lines if you want it.
- **Not an admin panel.** It returns JSON resources, nothing else.
- **Not a framework.** Every default is a `protected` method you can override, and when you need something genuinely different you write the action yourself and keep the other four.
